# Aqua Intelligence V2 — Architecture Brief

## Product objective
Aqua Intelligence is evolving from an NRW/leak-detection cockpit into a water-network engineering copilot.

The platform should understand natural-language engineering requests, determine the user's intent, route the request to the correct deterministic engine, and only use an LLM where language interpretation, summarisation, or reasoning is actually needed.

## Core flow
User / UI
→ Intent Engine
→ Command Router
→ one or more domain engines:
- GIS
- telemetry
- network topology
- hydraulics / EPANET
- DMA design
- leak/burst risk
- acoustics
- reporting / knowledge
→ optional AI explanation
→ validated response / map action

## Key design principle
The LLM is not the hydraulic solver and is not the source of engineering truth.

It may:
- interpret requests
- extract entities
- choose tools
- summarise deterministic results
- explain why a result was produced
- compare scenarios generated by engineering engines

It must not:
- fabricate sensor readings
- fabricate EPANET outputs
- fabricate elevations
- directly alter engineering state without validated commands
- silently invent missing network data

## Elevation and hydraulics
Elevation is a first-class property of the network model.

Future DMA and hydraulic workflows should account for:
- terrain/node elevation
- hydraulic grade
- static and residual pressure
- demand patterns
- pipe diameter/material/roughness
- headloss
- velocity
- pumps
- valves
- tanks/reservoirs
- boundary conditions

Example future request:
"Design a DMA around this estate, keep minimum pressure above 25 m, and minimise the number of inlet meters."

Expected orchestration:
1. select connected network subgraph
2. load elevations and demands
3. identify candidate boundary valves/meters
4. run hydraulic scenarios
5. reject infeasible candidates
6. rank feasible candidates by engineering criteria
7. show candidate boundaries and trade-offs on the map
8. generate a human-readable explanation from deterministic outputs

## Cloudflare direction
The target hosted architecture should remain compatible with Cloudflare:
- static/web app hosting
- Workers for server-side orchestration/API
- Workers AI for low-cost intent/reasoning
- optional AI Gateway for provider routing/observability
- future Vectorize/RAG if engineering documents are added

Provider access must sit behind interfaces so Cloudflare Workers AI, external frontier models, and eventually a local/private model can be swapped without rewriting the app.

## Demo objective
The V2 demo should prove orchestration, not just chatbot UI.

A strong demo flow:
1. "Show PVC pipes older than 20 years."
2. map/filter action executes.
3. "Why are these three sections high risk?"
4. deterministic data is gathered; AI explains it.
5. "Plan a 12-hydrophone lift-and-shift deployment."
6. deployment adapter returns a structured plan.
7. "Design a DMA here and keep pressure above 25 m."
8. the request routes to hydraulic/DMA engines; until the real solver is connected, the UI clearly shows that simulation is required rather than inventing a result.
